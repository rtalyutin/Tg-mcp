# G1/G2: что подтверждено и как проверить остальное

Дата повторной проверки источников: 19.09.2026. ТЗ: 0.19, разделы 3 и 11.

## Документальные основания

1. Веб-задачи могут пользоваться доступными своему чату подключёнными
   инструментами, навыками и плагинами. Локальная папка между запусками не
   гарантирована. Это подтверждает общий механизм, но не наличие доступа у
   конкретной задачи «Сказка доброго Медведя» и не разрешение на отправку.
   [OpenAI: Scheduled tasks](https://learn.chatgpt.com/docs/automations).
2. Официальное руководство описывает MCP Streamable HTTP, проверку через
   Inspector и подключение к ChatGPT после локальных тестов. Эти этапы
   различаются; локальный MCP-клиент не заменяет проверку в аккаунте.
   [OpenAI: Build an MCP server](https://developers.openai.com/plugins/build/mcp-server).
3. Аутентифицированный MCP предполагает OAuth 2.1: metadata ресурса и
   сервера авторизации, проверку токена, issuer/audience/expiry/scopes.
   OpenAI рекомендует готовый identity provider. Провайдер для проекта не
   выбран; самодельный OAuth и анонимный доступ не реализуются.
   [OpenAI: Authentication](https://developers.openai.com/plugins/build/auth).
4. Пакет `@modelcontextprotocol/sdk` закреплён на 1.30.0, полученной из npm
   в этом запуске. Репозиторий различает v1 и v2; код использует API v1,
   не смешивает поколения.
   [Официальный TypeScript SDK](https://github.com/modelcontextprotocol/typescript-sdk).

**Вывод:** общая поддержка подключённых инструментов в фоновых задачах
документирована. G1/G2 конкретного коннектора остаются BLOCKED: нет
развёрнутого аутентифицированного endpoint и результата реального запуска.
Локальный прототип подтверждает только транспорт и защиту тестового профиля.

## Воспроизводимая последовательность проверки

1. **Локальный gate (выполняется сейчас).** `npm ci --ignore-scripts`,
   `npm run check`, `npm test`. Инициализация официального MCP-клиента,
   список из одного read-only инструмента, чтение состояния, отрицательные
   проверки доступа/схем/размера, отсутствие инструмента отправки.
   Сохранить версии, digest исходников и результат тестов.
2. **Подготовка доступа.** Документированный путь защищённого MCP — OAuth 2.1.
   Разработчик сам проверяет документацию и готовит совместимую конфигурацию
   готового провайдера без хранилища прикладных публикаций. Скриншот настроек
   владельца не является предварительным условием этой работы. Конкретный
   провайдер ещё не выбран; создание аккаунта/ресурса не разрешено автоматически.
   Реальную поддержку в аккаунте проверить при подключении. Локальный Bearer
   не переносить в продакшен и не выдавать за подтверждённую альтернативу OAuth.
3. **Стенд на Timeweb (не выполнен).** После отдельного разрешения подготовить
   endpoint с реальной авторизацией, HTTPS, допустимыми Host/Origin,
   отключённой публикацией. Текущий loopback-only прототип напрямую не
   деплоится: сначала реализуется принятый профиль доступа.
4. **Ручное подключение (не выполнено).** В аккаунте владельца подключить
   endpoint штатным способом, завершить авторизацию, вызвать чтение.
   Сохранить время, версию, instance_id и фактический ответ, не токен.
5. **Фоновое чтение (не выполнено).** Только после разрешения на изменение
   действующей задачи сохранить её полный актуальный промпт и добавить
   временный вызов чтения. Не менять расписание/содержание сказок и не
   создавать дублирующую задачу. Дождаться реального фонового запуска;
   сохранить идентификатор запуска и ответ сервера. Не подменять его
   вымышленным ответом или ручным вызовом из другого чата.
6. **Проверка отправки (не выполнена).** После реализации ядра, проверки бота
   и отдельного разрешения владельца на конкретный тестовый канал/материал
   проверить одну синтетическую публикацию. Проверить подтверждённый
   message_id и фактическое наличие поста; затем — полный текст частями.
   Read-only gate не даёт права на публикацию. Не маскировать запись аннотацией
   чтения. Если платформа требует недоступного подтверждения, G1 непройден.

G1 — PASS только после фоновой разрешённой отправки с подтверждением в канале.
Если доступ/авторизация не работают — остановить зависимую интеграцию,
зафиксировать точную причину, продолжать независимое ядро и mock-тесты.
Менять генератор, расписание, место хранения или модель разрешений без
отдельного решения владельца нельзя.

## Что понадобится от владельца

На этом этапе скриншот и технический выбор от владельца не требуются.
После подготовки конкретной конфигурации разработчик указывает точное действие
подключения/входа, только если его нельзя выполнить доступными средствами.
Не просить владельца самостоятельно выяснять поддержанные протоколы.

Документация подтверждает общий механизм, а не доступ конкретной фоновой задачи.
В текущем чате инструменты нашего publisher не обнаружены; это не доказывает
отсутствие функции подключения в интерфейсе аккаунта. G1/G2 остаются открытыми
до реального endpoint, авторизации и фоновой проверки. Разрешений на деплой,
платные ресурсы и Telegram-отправки эта поправка не добавляет.
