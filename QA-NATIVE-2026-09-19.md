## Limited security review

Assets/boundaries: the bot token in the outbound URL; configured channel identity; untrusted HTTP/JSON replies; readiness consumed by a future publisher. Test data were synthetic and every operational HTTP fixture bound to `127.0.0.1`. No live Telegram or Timeweb API calls, task edits or deployment operations were performed by this reviewer; public documentation was read.

Observed/static conclusions within this scope:

- Exact HTTPS Telegram origin or explicit loopback HTTP test root; credential/query/fragment roots are rejected by shared validation. Redirects are refused. This constrains token egress. `apiRoot` remains a trusted internal configuration seam, not a user-supplied MCP argument.
- Readiness validates primitive types and exact channel/bot/administrator/posting-right identity, with a common failure result. It makes no write call, performs no retry and stores no readiness cache. The class has no logging path; synthetic error/token redaction was also tested dynamically. This does not audit a future host, proxy or telemetry agent.
- A 64 KiB response cap, fatal UTF-8 decoder and one bounded abort signal cover streamed response handling. Independent stream tests distinguish byte-limit rejection from ordinary timeout.
- The readiness module does not enforce readiness on the integrated publisher today: that harness still accepts test readiness input. Documents accurately disclose this. A future production composition root must gate sending and define refresh, concurrency and failure invalidation. A successful read is a snapshot, not a guarantee that later send permission remains valid.
- Shared sender option validation is the only modification to the existing send path; source and built UNKNOWN regression checks passed. No application persistence mechanism was added. `formatter.ts`, `publisher.ts`, `main.ts`, `server.ts` and `mcp-http.ts` match the baseline commit; the integrated-server source changes only its version constant.

No confirmed defect was found in the tested local gate. This was not a full application/dependency audit or a production security certification. No CVE scan was run; TLS deployment, real secret handling, public authentication and external rate limits were not tested.

Primary contract references checked 19.09.2026: Telegram documents [getMe](https://core.telegram.org/bots/api#getme), [getChatMember](https://core.telegram.org/bots/api#getchatmember) and [administrator posting rights](https://core.telegram.org/bots/api#chatmemberadministrator). These support the preparation instructions; they do not establish that this application's future platform configuration works.
