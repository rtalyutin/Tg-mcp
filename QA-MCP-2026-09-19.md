# Независимая приёмка локального MCP integration harness — 19.09.2026

**VERIFIED / PASS для локального MCP → Publisher → TelegramSender → mock HTTP.** Внешний Telegram, OAuth, Timeweb и доступ существующей фоновой задачи не проверялись. Этот результат не закрывает G1/G2 и не разрешает публикацию.

Исполнитель: отдельный QA-агент `verify_probe`, не автор production-изменения. Среда: Node.js v24.19.0, пакет 0.5.0, рабочая копия с базой Git `3f190255d37f784c39e69ef282d225d0d3698ac4`. Проверены изменённые и новые файлы рабочей копии, а не только base commit. Production-код проверяющий не редактировал; добавлены `test/mcp-heldout.test.ts` и этот отчёт.

Независимые новые сценарии: **4/4 PASS**. Общая регрессия: **61/61 PASS**, 0 FAIL, 0 SKIP. TypeScript: PASS. Новые проверки используют raw `node:http` и независимый mock HTTP; авторские MCP helpers и SDK client не используются как oracle. Каждое обращение создаёт отдельное HTTP-соединение без клиентского session cache.

| Проверяемое требование | Наблюдаемое доказательство |
| --- | --- |
| Три MCP-инструмента и строгие схемы | `tools/list` возвращает только get_publisher_status, publish_story, get_publish_attempt; input/output schemas запрещают дополнительные поля |
| Честные annotations | publish_story имеет readOnlyHint=false, idempotentHint=false, openWorldHint=true; оба чтения имеют readOnlyHint=true |
| Один Publisher на жизнь harness | Пока первая mock-отправка удерживается, независимые HTTP-соединения читают тот же IN_PROGRESS, канонический attempt_id; другая сказка получает BUSY |
| Регистрация до отправки и отсутствие повторов в полёте | До освобождения первой отправки mock получает ровно один POST; replay с новым attempt_id той же сказки ничего не добавляет |
| Последовательная публикация полного текста | После освобождения первой части mock получает части А×4096, Б×4096, В; конкатенация точно равна входу; единственный настроенный chat_id соблюдён |
| Стабильность instance и replay | После отправки статус содержит исходный instance_id; replay возвращает сохранённый PUBLISHED и не увеличивает число POST |
| PARTIAL и UNKNOWN сохраняются | После подтверждения первой части mock отвечает429 либо500; возвращаются PARTIAL либоUNKNOWN, remaining_parts=1, корректный uncertain_part_index; третья часть не отправляется |
| Отсутствие скрытых повторов после ошибки | Чтение и replay из новых HTTP-соединений, включая новый attempt_id той же сказки, сохраняют результат; mock остаётся на двух запросах |
| Auth, лишний chat_id/force, невалидные поля | Неверный Bearer отклонён401; ошибочные аргументы отклоняются MCP; mock не получает запросов |
| Stale instance / неизвестная попытка | Stale publish возвращает UNKNOWN/INSTANCE_CHANGED/remaining_parts=null; неизвестное чтение — ATTEMPT_NOT_KNOWN; отправок нет |
| Только loopback mock root | Реальный api.telegram.org, внешний хост, HTTPS-loopback, localhost, credentials и query в root отклонены до старта harness |
| Прежний read-only профиль | Старые raw/SDK тесты и CLI guards вошли в полную регрессию; main по статическому чтению вызывает только startLocalProbe, публикация через него не включается |

Статический разбор подтверждает создание одного Publisher и одного TelegramSender вне per-request `registerTools`; callbacks всех MCP-запросов замыкаются на эти объекты. HTTP listener привязан к 127.0.0.1. Наблюдение общих состояний между независимыми соединениями подтверждает поведенческую часть этого вывода.

## Границы результата

Открытых наблюдаемых дефектов в принятом scope не найдено. Полное падение процесса, долгоживущие запросы после разрыва клиентского соединения, реальный TLS/DNS и поведение reverse proxy этим новым gate отдельно не моделировались. Общая регрессия включает прежние локальные тесты adapter timeout/disconnect/redirect, но они не заменяют внешнюю интеграционную приёмку.

Состояние Telegram readiness в harness задаётся тестовой конфигурацией, а не реальной проверкой прав бота. Локальный Bearer не является OAuth. Сохранения попыток между рестартами и глобальной защиты от дублей не обещается. Документация и README могут обновляться координатором после этого отчёта; настоящий verdict привязан к перечисленным source hashes и исполненным тестам.
