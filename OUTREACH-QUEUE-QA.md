## Требования и версия

Очередь применяется ко всем прежде ограниченным динамическим маршрутам, прежние исключения health/static сохранены. Проверка аутентификации и бизнес-действия происходят после допуска. Новое решение имеет приоритет над историческими записями о неутверждённой очереди.

## Q-01 — пропущенные записи окончательных 429 (FIXED / VERIFIED)

Место исходной версии: `src/outreach/server.ts:63–69`, условие `rateLogs.size >= admissionQueueLimits.total` возвращает управление без записи очередного события.

Требование: ТЗ §8.2, `YCS_Outreach_TZ_v1.md:205`: массовые отклонения разрешено агрегировать с **точным счётчиком**, первой/последней отметкой времени, без выборочного пропуска. Исключение при полном отказе хранилищ не относится к проверенному сценарию: зависимость просто задержана, после чего все операции успешно выполняются.

Воспроизведение: удержать четыре запроса допуска одного IP; задержать завершение записи audit; последовательно выполнить 70 дополнительных HTTP-запросов, каждый получает 429; отменить четыре ожидания; разрешить завершение audit и закрыть приложение. Наблюдение: 64 завершившиеся записи вместо 70. Никакие бизнес-репозитории не вызываются.

Регрессионный сценарий: `held-out queue HTTP: every overflow remains counted when audit writes are delayed but succeed`, файл `test/outreach-queue-heldout.test.ts`. Требуемый результат — 70 событий либо эквивалентный точный агрегат.

Автор убрал cap у `rateLogs`: в финальном `src/outreach/server.ts:63–69` каждому окончательному HTTP 429 соответствует вызов записи, завершение SQL не задерживает HTTP-ответ. Внутренние попытки допуска по-прежнему не журналируются как HTTP-отказы (`server.ts:51,99`). Проверяющий продуктовый код не менял. Повтор того же held-out сценария дал **70/70** после завершения всех успешно задержанных записей; остальные восемь тестов также прошли. Дефект закрыт для указанного финального fingerprint.

## Пределы и остаточные риски

- Ограничение 4/IP и 64 всего реализовано в памяти **каждого экземпляра**. Между экземплярами общим является интервал PostgreSQL; единая глобальная очередь и FIFO между процессами не проверены и не заявляются.
- Тест двух приложений использует два HTTP-экземпляра в одном Node-процессе и общий `pg.Pool`. PGlite не доказывает native PostgreSQL-конкурентность, изоляцию соединений/процессов или восстановление после настоящей серверной SQL-ошибки.
- Close отменяет ожидание клиента, но `drained()` ждёт завершения уже начатой операции зависимости. В тесте она была явно освобождена; ограниченное время shutdown при зависшей сети к реальной БД не подтверждено.
- Исправление Q-01 снятием отдельного cap audit восстанавливает точность, но оставляет потенциально неограниченный backlog audit Promise / ожидающих `pg`-операций при медленной БД. Лимит pool=8 ограничивает соединения, а не число ожидающих записей. Незавершённые записи могут быть потеряны при аварийном завершении процесса. Без отдельного resource budget/SLO и измерения это остаточный риск, не установленный нагрузочный отказ. Нельзя объявлять всё приложение ограниченным по ресурсам только на основании admission queue.
- Реальные ChatGPT/Codex, HTTPS/Timeweb, private PostgreSQL, прокси/IP и платформенные журналы не проверялись. Успех обычного локального SDK снимает только воспроизведённый локальный handshake-сбой, не весь gate stage1.
- Очередь почтовых отправок, почта и Telegram не входят в эту проверку.
