## Фактические проверки

1. **Запрос:** ровно один POST, корректный endpoint с `botTOKEN/sendMessage`,
   сохранённый префикс локального API root, точные `chat_id` и Unicode-текст
   с CRLF/кавычками/обратным слешем. В JSON нет `parse_mode` и токена; токен
   не возвращается в результате адаптера. Токен присутствует в URL локального
   запроса, как требует протокол Bot API.
2. **Матрица классификации:** HTTP 400/404/409/422 → `SEND_REJECTED`,
   401/403 → `BOT_FORBIDDEN`, 429 → `RATE_LIMITED`; проверены также соответствующие
   Telegram `ok=false,error_code` внутри HTTP 200. HTTP 201/202/204/205/206,
   408 и 5xx дают `unknown`. Невалидные `ok`, `result`, `message_id`, типы полей
   и неоднозначные ошибки не подтверждают отправку. Максимальный положительный
   safe integer для message ID принят.
3. **Тело ответа:** невалидные JSON/UTF-8, превышение 64 KiB как по заголовку,
   так и при chunked-передаче, незавершённое объявленное тело дают `unknown`.
4. **Граница размера:** валидный JSON с пробельным заполнением ровно до 64 KiB
   подтверждает отправку; добавление одного байта в chunked-тело даёт `unknown`.
5. **Сетевые сбои:** таймаут ожидания заголовков, таймаут после начала тела
   и разрыв сокета дают `unknown`. Счётчик полученных HTTP-запросов не увеличивается
   от скрытого повтора; все операции завершились в заданном тестовом пределе.
6. **Перенаправления:** HTTP 301/302/303/307/308 дают `unknown`;
   отдельный сервер-назначение не получил ни одного запроса.
7. **Конфигурация:** отвергнуты внешние/подменённые хосты, userinfo, query/fragment,
   неправильный протокол/порт, URL-инъекции через токен и неверные таймауты.
8. **Жизненный цикл тела:** при отказе из-за объявленного размера, HTTP 400 и 503
   незавершённый поток ответа закрывается после возврата адаптера. Проверена
   фактическая server-side `close`, до истечения настроенного таймаута 2 секунды.
9. **Publisher + реальный форматтер + HTTP:** длинный текст разбит на три части;
   первая подтверждена, на второй соединение разорвано. Результат `UNKNOWN`,
   верные ID/индекс/остаток; обязательна ручная проверка, автоматический повтор
   запрещён. Третья часть не отправлена. Повтор запроса и новый attempt ID той же
   сказки не создают дополнительных HTTP-запросов.

## Замечания при проверке

До окончательного прогона автору указано, что его исходная mock-очередь
мутировала массив, по длине которого шёл цикл матрицы; это ограничивало
достоверность покрытия. Автор исправил счётчик. Также выявлено расхождение
между ожидаемым авторским тестом для HTTP 201 и первоначальным классификатором;
автор закрепил консервативное правило подтверждения только HTTP 200.
Окончательная независимая матрица проверяет это правило на текущих байтах.
Открытых дефектов в проверенной области не обнаружено.

## Ограничения доказательства

- Mock подтверждает поведение адаптера на локальном HTTP; TLS/DNS, реальные
  ограничения Telegram, права бота и свойства реального канала не проверены.
- Для явных HTTP 4xx кроме 408 статус считается окончательным отказом независимо
  от тела. Ограничение разбора тела относится к кандидатам на успешный ответ;
  неподходящие статусы отменяют чтение тела.
- Отсутствие токена в JSON/результате и запрет перенаправлений проверены. В коде
  адаптера нет логирования. Это не аудит логов будущего reverse proxy, APM или
  инфраструктуры: поскольку токен входит в URL Bot API, там потребуется редактирование
  или отключение журналирования секретных URL.
- Счётчик HTTP-запросов доказывает отсутствие повторного application POST в
  проверенных сценариях; он не описывает низкоуровневые TCP retransmissions.
- OAuth, MCP-интеграция записи и фоновый вызов ChatGPT этим результатом не
  подтверждаются. Развёртывание и настоящая публикация не включены.
- Память попыток остаётся оперативной: глобальной защиты от дублей после
  перезапуска нет.
