# Timeweb App Platform без собственного Dockerfile

Объект: пакет 0.8.0, 19.09.2026. Production composition root реализован и
локально проверен с synthetic OAuth/Telegram. Реальный деплой не выполнялся.
Внешний профиль — production-main/app.js; старый локальный probe не выставлять
через публичный reverse proxy. Полная конфигурация — OAUTH-SETUP.md.

## Подтверждено документацией

Timeweb поддерживает Node.js 24 в профиле Express; App Platform сама
собирает контейнер и настраивает внешний адрес. Собственный Dockerfile не
нужен. Приложение должно слушать 0.0.0.0 и предоставлять HTTP endpoint.
Проверено 19.09.2026:
[Node.js/Express](https://timeweb.cloud/docs/apps/deploying-backend-applications/express),
[устройство App Platform](https://timeweb.cloud/docs/apps/how-it-works).

Нативный профиль автоматически выполняет npm install и запускает PM2.
Нужно проверить итоговые команды/логи платформы перед первым разрешённым
выпуском: наличие lockfile само по себе не доказывает воспроизводимость
автоматической установки. PM2 должен запускать один процесс, без cluster,
дополнительных реплик и перекрывающегося rolling reload: RAM-дедупликация
между процессами не общая.

## Подготовленная сборка

```sh
npm ci --include=dev --ignore-scripts
npm run check
npm test
npm run build
```

`tsconfig.build.json` компилирует только src в dist и переписывает относительные
импорты .ts в .js. `npm run start:built` запускает скомпилированный локальный
read-only probe. Это проверка сборки, а НЕ команда внешнего production-запуска.
`NODE_ENV=production`, внешний HOST и включение публикаций по-прежнему
отклоняются. Не снимать эти ограничения для обхода незавершённой авторизации.

Production composition root в режиме publisher создаёт один Publisher и один
TelegramSender. В readonly он их вообще не создаёт. TelegramReadinessChecker проверяет getMe → getChat →
getChatMember: точный числовой ID канала, тип channel, идентичность бота,
status=administrator и can_post_messages=true. Любая неоднозначность даёт
TELEGRAM_NOT_READY. Модуль подключён к startLocalCheckedPublisher на loopback mock;
старый harness с ручной готовностью сохранён только как тестовая фикстура.
Production entrypoint использует эту же проверку. Результат — моментальный
снимок, а не гарантия последующей доставки; права могут измениться.
Контракт проверен по [Telegram Bot API](https://core.telegram.org/bots/api#chatmemberadministrator)
19.09.2026. Обложка и права на stories не относятся к публикации текстовых постов.

В checked-профиле проверка выполняется при чтении статуса и перед первой
отправкой каждой новой попытки; одновременные проверки объединяются, завершённый
успех не кэшируется. Блокировка и реестр охватывают ожидание прав; ошибка сбрасывает
готовность, поздний ответ после сброса/stop её не возвращает. Компоненты
переиспользованы в production composition root без ручного флага readiness. При перезапуске — новый instance_id и пустой реестр; не
воспроизводить прошлые сказки автоматически.

В production-main подключён installShutdownHandlers(app.close). Сначала
блокируются новые попытки/части; текущий запрос дорабатывает до ответа/таймаута,
после него закрывается HTTP. Stop не отзывает отправленное: подтверждённые ID
сохраняются, неподтверждённый исход остаётся UNKNOWN. Реальный grace period
Timeweb пока не проверен; принудительный SIGKILL теряет RAM и оставляет исход
неизвестным. Не включать rolling overlap нескольких экземпляров.

TELEGRAM_BOT_TOKEN и фиксированный TELEGRAM_CHANNEL_ID потребуются только на разрешённом
внешнем этапе. PUBLISH_ENABLED=false и MCP_PROFILE=readonly по умолчанию. Переменные OAuth
описаны в OAUTH-SETUP.md; проверять npm run check:config. Не заменять OAuth
тестовым LOCAL_PROBE_TOKEN (production-config отвергает его). Не логировать исходящие URL
Bot API: они содержат токен. Не логировать текст/тела запросов.

## Порядок внешнего подключения

1. Выполнить подготовленную настройку готового IdP по OAUTH-SETUP.md.
   Для первого подключения подготовлен путь Auth0; tenant/аккаунт ещё не созданы.
   Техническую конфигурацию готовит разработчик; нужен реальный вход владельца.
2. После отдельного разрешения создать backend на Timeweb с записью выключенной,
   проверить HTTPS, auth, /healthz, отклонение неавторизованных запросов.
3. Проверить ручной read-only MCP-вызов, затем отдельно вызов из фоновой задачи
   с уникальным маркером и серверным подтверждением. Только второй закрывает G1.
   Действующую задачу генерации на этапе проверки не переписывать.
4. После отдельного разрешения на публикацию выполнить G3 в тестовом канале:
   полный длинный текст, порядок/ID сообщений, остановка при неопределённости.
5. Только при доказанных G1/G2/G3 применить блок `PUBLISHING-HANDOFF.md`
   к существующей задаче. Не менять её творческие инструкции и расписание.

Локальная подготовка завершена в объёме 0.8.0. Следующий внешний шаг — вход
владельца в Timeweb Cloud для подготовки приложения из GitHub. Тариф/создание
ресурса подтверждаются отдельно. Затем настройка IdP и подключение ChatGPT;
до G1–G3 перенос публикации на инструмент не включать.
