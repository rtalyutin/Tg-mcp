# Timeweb App Platform без собственного Dockerfile

Объект: пакет 0.6.0, 19.09.2026. Это подготовка сборки и подключения;
production-сервер ещё не реализован. Не запускать текущий локальный probe
через публичный reverse proxy. Реальный деплой не выполнялся.

## Подтверждено документацией

Timeweb поддерживает Node.js 24 в профиле Express; App Platform сама
собирает контейнер и настраивает внешний адрес. Собственный Dockerfile не
нужен. Приложение должно слушать 0.0.0.0 и предоставлять HTTP endpoint.
Проверено 19.09.2026:
[Node.js/Express](https://timeweb.cloud/docs/apps/deploying-backend-applications/express),
[устройство App Platform](https://timeweb.cloud/docs/apps/how-it-works).

Нативный профиль автоматически выполняет npm install и запускает PM2.
Нужно проверить итоговые команды/логи платформы перед первым разрешённым
выпуском: наличие lockfile само по себе не доказывает воспроизводимость
автоматической установки. PM2 должен запускать один процесс, без cluster,
дополнительных реплик и перекрывающегося rolling reload: RAM-дедупликация
между процессами не общая.

## Подготовленная сборка

```sh
npm ci --include=dev --ignore-scripts
npm run check
npm test
npm run build
```

`tsconfig.build.json` компилирует только src в dist и переписывает относительные
импорты .ts в .js. `npm run start:built` запускает скомпилированный локальный
read-only probe. Это проверка сборки, а НЕ команда внешнего production-запуска.
`NODE_ENV=production`, внешний HOST и включение публикаций по-прежнему
отклоняются. Не снимать эти ограничения для обхода незавершённой авторизации.

## Настройки будущего backend-приложения

| Поле | Значение / состояние |
|---|---|
| Репозиторий | rtalyutin/Tg-mcp; перед реальным запуском владелец планирует сделать приватным |
| Источник | выбранный проверенный commit main, без автоматического выпуска новых commits во время приёмки |
| Тип | Backend, Node.js/Express, Node.js 24 |
| Собственный Dockerfile | не используется |
| Сборка | npm ci --include=dev --ignore-scripts && npm run build; проверить порядок команд платформы |
| Production entrypoint | ещё не реализован; его команда будет указана после G2 |
| Интерфейс и порт | будущий сервер 0.0.0.0, PORT по настройкам платформы |
| Масштаб | ровно один процесс / одна реплика |
| MCP | /mcp, TLS на платформе; аутентификация по G2 |
| Healthcheck | /healthz без текста, токенов и сведений о канале |
| Постоянный диск/БД/очередь | не нужны, не подключать |
| Секреты | только переменные среды платформы; не Git, не команды shell |

Будущий production composition root должен создать один Publisher и один
TelegramSender. TelegramReadinessChecker проверяет getMe → getChat →
getChatMember: точный числовой ID канала, тип channel, идентичность бота,
status=administrator и can_post_messages=true. Любая неоднозначность даёт
TELEGRAM_NOT_READY. Этот модуль готов, но пока не подключён к production:
в loopback harness readiness остаётся тестовым входом. Результат проверки —
моментальный снимок, а не гарантия последующей доставки; права могут измениться.
Контракт проверен по [Telegram Bot API](https://core.telegram.org/bots/api#chatmemberadministrator)
19.09.2026. Обложка и права на stories не относятся к публикации текстовых постов.

Production-интеграция обязана проверять права до первой отправки попытки,
сбрасывать readiness при любой неуспешной проверке и не запускать sender при
false. TTL/обновление snapshot и конкурентные проверки нужно реализовать и
проверить отдельно. При перезапуске — новый instance_id и пустой реестр;
не воспроизводить прошлые сказки автоматически.

TELEGRAM_BOT_TOKEN и фиксированный TELEGRAM_CHANNEL_ID потребуются только на разрешённом
внешнем этапе. PUBLISH_ENABLED=false по умолчанию. Конкретные переменные
OAuth зависят от поддержанного клиентом механизма (G2); не придумывать их и
не заменять OAuth тестовым LOCAL_PROBE_TOKEN. Не логировать исходящие URL
Bot API: они содержат токен. Не логировать текст/тела запросов.

## Порядок подключения после разработки production-профиля

1. Подготовить стандартный OAuth 2.1 по официальной документации OpenAI и
   совместимому готовому провайдеру. Разработчик исследует технические варианты
   самостоятельно; скриншот настроек не блокирует подготовку. Провайдер и
   его внешняя настройка пока не выбраны/не выполнены.
2. После отдельного разрешения создать backend на Timeweb с записью выключенной,
   проверить HTTPS, auth, /healthz, отклонение неавторизованных запросов.
3. Проверить ручной read-only MCP-вызов, затем отдельно вызов из фоновой задачи
   с уникальным маркером и серверным подтверждением. Только второй закрывает G1.
   Действующую задачу генерации на этапе проверки не переписывать.
4. После отдельного разрешения на публикацию выполнить G3 в тестовом канале:
   полный длинный текст, порядок/ID сообщений, остановка при неопределённости.
5. Только при доказанных G1/G2/G3 применить блок `PUBLISHING-HANDOFF.md`
   к существующей задаче. Не менять её творческие инструкции и расписание.

Действий владельца для продолжения подготовки сейчас не требуется. При реальном
подключении дать точную инструкцию входа/разрешения доступа, если его нельзя
выполнить доступными средствами. Доступ к Timeweb и Telegram пока не нужен.
