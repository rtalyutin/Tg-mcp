# OAuth и подключение: пакет 0.8.0

Подготовлена серверная сторона OAuth 2.1; реальная связка ещё не подключена.
Приложение — resource server. Вход, согласие, authorization code + PKCE S256,
выдачу/обновление токенов выполняет готовый внешний IdP. Самодельного сервера
выдачи токенов, пользователей или паролей в приложении нет.

## Подготовленная конфигурация провайдера

Для первого подключения подготовлен путь через Auth0. Аккаунт/tenant не созданы,
тариф и доступность для владельца не подтверждены; ниже конфигурация для
выполнения после разрешения, а не отчёт о настройке. Можно использовать уже
имеющийся совместимый IdP с тем же контрактом JWT; писать собственный OAuth не нужно.

1. В отдельном tenant создать API `Telegram Story Publisher` с Identifier,
   равным точному внешнему `https://<app-domain>/mcp`. Алгоритм RS256;
   access token — подписанный JWT, не opaque/зашифрованный токен.
2. Задать scopes `stories:read` и `stories:write`. Разрешить их только владельцу
   и зарегистрированному клиенту ChatGPT. В приложение передать точный User ID
   владельца в `OAUTH_ALLOWED_SUBJECT`: чужой пользователь того же tenant тоже
   получает отказ. Проверяется именно claim `scope`, не массив `permissions`.
3. Включить Resource Parameter Compatibility Profile и Include Issuer in
   Authorization Responses. `resource` из ChatGPT должен стать `aud` токена;
   issuer в ответах и discovery должен совпадать буквально, включая `/`.
4. Использовать manual CIMD registration: зарегистрировать точный актуальный
   документ клиента ChatGPT и дать ему per-app доступ к API. Discovery должен
   объявлять S256 и поддержанный способ аутентификации клиента. Не разрешать
   всем сторонним приложениям доступ по умолчанию. Если выбран predefined client,
   копировать redirect URI с экрана управления MCP, не угадывать callback ID.
5. Разрешить необходимые OIDC scopes, которые провайдер объявляет для клиента;
   обновление токенов, если требуется фоновому клиенту, настраивается у IdP.
   Refresh token не хранится и не обрабатывается нашим приложением.

Основание, проверено 19.09.2026:
[OpenAI Authentication](https://developers.openai.com/plugins/build/auth),
[официальный OpenAI scaffold с Auth0](https://github.com/openai/openai-mcpkit/blob/main/python-authenticated-mcp-server-scaffold/README.md),
[Auth0 MCP authorization](https://auth0.com/ai/docs/mcp/get-started/authorization-for-your-mcp-server),
[MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization).
Эти документы подтверждают технический путь, не фактическую доступность
аккаунта/опций/фонового вызова конкретного владельца.

## Значения приложения

Шаблон `.env.production.example` содержит только заглушки. Приложение само
не читает `.env`: вводить значения через защищённые переменные платформы.

| Переменная | Значение/правило |
| --- | --- |
| `MCP_RESOURCE_URL` | Точный HTTPS URL `/mcp`, без query/fragment |
| `OAUTH_ISSUER` | Точный issuer из discovery, например `https://tenant.auth0.com/` |
| `OAUTH_JWKS_URI` | Фиксированный HTTPS JWKS на том же origin, что issuer |
| `OAUTH_ALLOWED_SUBJECT` | Единственный допущенный subject владельца |
| `MCP_PROFILE` | `readonly` по умолчанию; `publisher` после отдельной настройки |
| `PUBLISH_ENABLED` | `false` по умолчанию; только буквальное `true` разрешает отправку |
| `PORT`, `HOST` | Порт платформы, по умолчанию 8080; HOST только `0.0.0.0` |
| `TELEGRAM_BOT_TOKEN` | Только для publisher, хранить в переменных платформы |
| `TELEGRAM_CHANNEL_ID` | Фиксированный отрицательный числовой ID, только для publisher |

`readonly` создаёт только `get_publisher_status`, не создаёт sender/checker
Telegram и запрещает `PUBLISH_ENABLED=true`. В `publisher` доступны три
инструмента, но запись всё равно требует write scope и включённого флага.
`get_publisher_status`/`get_publish_attempt` требуют read scope.

## Что проверяет сервер

На каждом MCP HTTP-запросе проверяются подпись RS256/ES256, точные issuer/audience,
обязательные iss/aud/sub/exp/iat, сроки exp/nbf/iat, subject и read scope.
Перед dispatch срок проверяется повторно, перед публикацией — write scope.
Без прав никакая попытка и Telegram-запрос не создаются.

JWKS берётся только из конфигурации; `jku`/`x5u` из JWT не управляют запросами.
Deadline 5 секунд, тело до 128 KiB, redirects запрещены. Ключи кэшируются только
в RAM до 5 минут, unknown kid ограничен cooldown 30 секунд. Плановая ротация
должна некоторое время публиковать оба ключа; экстренный отзыв старого JWT
может потребовать рестарт. Мгновенная ревокация JWT не обещается.

Публичны только минимальный `/healthz` и resource metadata в
`/.well-known/oauth-protected-resource/mcp` (также корневой alias).
Challenge/metadata используют фиксированный config, не Forwarded/Host.
Host обязан совпадать с внешним доменом; Origin отсутствует либо равен origin
приложения. TLS завершает Timeweb proxy; прямой HTTP-порт извне не открывать.
Proxy должен сохранять Host и Authorization. Его реальная конфигурация ещё
не проверена. CORS для браузерного JavaScript не включён: клиент MCP серверный.

Сервер не логирует тексты/токены/URL Bot API. На стороне платформы отключить
запись Authorization/тел запросов и редактировать исходящие Bot API URL в APM.
Stateless MCP не означает постоянную дедупликацию: registry/ключи только в RAM.

## Воспроизводимая проверка перед подключением

Локально: `npm ci --include=dev`, `npm run check`, `npm test`, `npm run build`.
После ввода конфигурации: `npm run check:config`. Это только синтаксическая
проверка, не проверка секретов, аккаунтов, сети или реальных разрешений.
Запуск подготовленного JS: `npm run start:production` или `node app.js`.
Команда `npm start` сохраняет прежний локальный probe и не предназначена для Timeweb.

После отдельно разрешённого размещения с `readonly`:

1. Проверить HTTPS `/healthz` → 200 и metadata → config; MCP без токена → 401
   с `WWW-Authenticate`. Неверный Host/Origin → 403. Никаких Telegram-секретов.
2. Добавить внешний `/mcp` как подключение ChatGPT, пройти вход владельцем.
   Проверить единственный read-only инструмент, instance_id и false/false.
   Успешный ручной вызов фиксирует только ручной доступ.
3. Проверить реальный запуск фоновой задачи с этим подключением: сохранить
   tool trace/время/instance_id, сравнить с работающим процессом. Ответ модели
   без вызова инструмента не доказательство G1. Не менять генератор ради probe;
   отдельный временный запуск/задача требует конкретного согласования.
4. Только после G1/G2 подключать Telegram и отдельно разрешать G3: полный
   многочастный текст в согласованном канале, сравнение текста/порядка/ID.
5. При успешном G3 применить подготовленный блок `PUBLISHING-HANDOFF.md`
   к действующему генератору без изменения его творческих инструкций.
   До активации сверить фактическое расписание с ожидаемым выпуском.

Реальная публикация, внешний деплой и вход владельцем в этом пакете не выполнены.
Следующий внешний шаг: вход владельца в Timeweb Cloud для подготовки приложения
из выбранного GitHub-репозитория. Создание платного ресурса — отдельное решение
после просмотра тарифа; технические настройки готовит разработчик.
