## Scope and trust boundaries

Inputs were the agreed single-owner publisher contract, the existing 0.7.0 behavior and the new OAuth implementation. The relevant boundary is untrusted HTTP/JWT/tool input entering a server with permission to publish to one configured channel. The owner is selected by exact issuer, audience and allowlisted subject; read and write scopes are checked on the server. The IdP owns login, authorization-code/PKCE exchange, token issuance and refresh. The application is only a resource server.

Static inspection traced those boundaries through `oauth.ts`, `oauth-server.ts`, `publisher-runtime.ts`, `production-config.ts`, `production-main.ts` and `app.js`. JWT verification delegates to `jose`; the package author's [jwtVerify documentation](https://github.com/panva/jose/blob/main/docs/jwt/verify/functions/jwtVerify.md) was consulted on 19.09.2026. The exact executed package version is established by the lockfile and local installed package, not by the moving documentation branch. No advisory scan or external penetration test is claimed.

## Findings and limits

No mandatory-criterion defect was observed in this local gate; no risk exception was needed. The tests establish server behavior using synthetic JWTs, mock JWKS and mock Telegram. They do **not** establish a real IdP authorization-code/PKCE/refresh flow, Auth0 account configuration, HTTPS/proxy behavior on Timeweb, authenticated access from the actual scheduled ChatGPT task, real channel permissions or real delivery. No real external operation was started. Those integration gates remain open; a manual call cannot close the background-access gate.

The JWT verifier's configured key cache and cooldown are present; provider key rotation/revocation and account-side policy were not exercised. Deduplication remains process-local and is lost on restart. Illustration handling is unchanged and outside this gate. This result is not authorization for deployment, resource creation, task activation or publication.
