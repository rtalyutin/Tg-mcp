## Находки и ограничения доказательств

### H-01 — изоляция схем в локальном harness нарушена (FIXED / VERIFIED)

Место: исходный `scripts/test-outreach.mjs:10–19` создаёт одну PGlite для всех файлов, а фикстуры рассчитывают на `pg.Pool({ options: '-c search_path=…' })`.

Воспроизведение: `node scripts/test-outreach.mjs --test-timeout=15000 test/outreach-access.test.ts test/outreach-heldout.test.ts`. Access-набор прошёл 14 проверок; настройка held-out получила `LOGIN_CAPACITY_REACHED`, хотя создала новую случайную схему. Она увидела восемь допусков из предыдущего файла.

Отдельный минимальный пример без продуктового кода подтвердил причину: два pg.Pool со startup options `search_path=heldout_a` / `heldout_b` получили `SHOW search_path = public`; таблица, созданная через первый pool, оказалась в namespace `public`.

Влияние: прежний общий локальный прогон недостоверен как изолированная проверка; наличие `CREATE SCHEMA` не обеспечивает ожидаемую изоляцию в этом адаптере. Это подтверждённый дефект инструмента проверки, **не установленный дефект приложения на native PostgreSQL**.

Исправление координатора: текущий `scripts/test-outreach.mjs:28–39` создаёт отдельную временную БД на файл; путь с явно предоставленной native PostgreSQL сохранён. Held-out файл добавлен в штатный набор. Независимая перепроверка: `npm run test:outreach` на окончательном fingerprint — все четыре файла, 42/42 PASS, 0 skipped; загрязнение отсутствует. H-01 закрыт только для PGlite harness. Семантика native sessions/schemas остаётся непроверенной.

### L-02 — SQL-error recovery через PGlite TCP не подтверждено

Первоначальный held-out сценарий добавлял `CHECK (entity_type <> 'contact')` к `outreach_audit`, затем вызывал сохранение контакта, чтобы PostgreSQL отверг audit после INSERT. После ожидаемого отказа TCP-адаптер выдал `Received unexpected parseComplete message from backend`; результаты следующих SELECT оказались сдвинутыми между ожидаемыми таблицами. Сценарий нельзя считать ни доказанным нарушением rollback приложения, ни PASS.

Для разрешённой локальной проверки применена инъекция ошибки драйвера после реального business INSERT. Этот вариант прошёл. Настоящая ошибка SQL в середине транзакции, восстановление подключения и повтор обязаны проверяться на native PostgreSQL. Исходный отказ не скрыт и не засчитан в успешные проверки.

### Блокировки этапа

- **Реальные ChatGPT и Codex — BLOCKED.** Подключение к двум продуктам по HTTPS URL с query не выполнялось. Управляемый local SDK pacing не доказывает совместимость. Обычный SDK handshake локально получает `RATE_LIMITED` при строгом 1/1000 мс; требуемый лимит не ослаблялся.
- **Native PostgreSQL — BLOCKED.** Нет доказательств многопроцессной блокировки/гонок, native startup options, server SQL-error recovery, рестарта БД, миграции на внешней БД, сохранности при деплое и backup/restore. PGlite не заменяет эти проверки. Точная внешняя граница 999/1000 мс не измерена.
- **Timeweb / HTTPS / proxy logs — BLOCKED.** Нет фактической TLS-цепочки, доверенной цепочки прокси Timeweb и проверки секретного маркера в платформенных access/error logs. Локальный loopback со специально доверенным proxy fixture подтверждает только выбранную ветку кода.
- **Визуальный браузерный smoke — не выполнялся этим исполнителем.** HTML/HTTP-проверка и статическое экранирование не доказывают работу JS и отрисовку. Сообщение координатора о недоступном Chromium — отдельное ограничение, не браузерный PASS.
- **Почта / реальные внешние эффекты — NOT_APPLICABLE к локальному stage1.** Транспорт намеренно отсутствует; отправок не было. Сквозной PoC раздела 11 не доказан.

Статический обзор затронутых файлов не нашёл подтверждённого обхода owner-прав или whitelist. Это ограниченный обзор, не полный аудит зависимостей или сертификат безопасности. Установленных дефектов продуктового кода в выполненном наборе нет.
