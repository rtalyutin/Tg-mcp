# Рекламный PoC: первый локальный срез

Основа: YCS_Outreach_TZ_v1.md, версия 1.3 от 20.09.2026, с согласованной
22.09.2026 очередью допуска. Первый этап опубликован в `main`; это не завершённый почтовый PoC.

## Что реализовано

- Общий HTTP/MCP-шлюз: `/mcp?login=<percent-encoded-secret>`. В настройках
  коннектора — No Authentication; сервер самостоятельно проверяет секрет.
- Секрет из 16 случайных спецсимволов; Argon2id с солью, до 8 активных допусков;
  отзыв действует на следующий запрос. Исходный логин не хранится в БД.
- Неизвестный допуск: изолированная заглушка, журнал без query, отсутствие
  бизнес-мутаций. Вне белого списка видны только общие метаданные MCP.
- Общий лимит 1 запрос / 1000 мс / IP во внешней PostgreSQL. Перед ним —
  ограниченная очередь: до 4 ожидающих допуска запросов с IP, до 64 на экземпляр,
  до 5 секунд ожидания. Переполнение/истечение срока дают 429 и Retry-After: 1.
  Смена маршрута, логина или процесса не сбрасывает общий лимит PostgreSQL.
- Вход владельца по логину/паролю, хеш пароля в БД, сессия 12 часов,
  HttpOnly/Secure/SameSite cookie, CSRF. Секрет MCP не выдаёт права владельца.
- Реестр: кандидаты, подтверждение/связывание владельцем, компании, источники,
  контакты, отдельные переговоры со статусами, таблица и карточка.
- Атомарные request_id, конфликт версий, аудит. Домен/название не служат
  достаточным основанием автоматического объединения компаний.

Шесть MCP-инструментов: `search_companies`, `get_company`,
`upsert_company_candidate`, `save_contact`, `create_opportunity`, `get_operation`.
Инструменты одобрения/отправки отсутствуют. Почтовый транспорт, черновики,
согласования и IMAP ещё не реализованы; `MAIL_TRANSPORT_ENABLED=true` отклоняется.

## Очередь допуска и проверка подключения

Раньше `notifications/initialized`, отправленный SDK сразу после `initialize`,
получал 429. Теперь все ранее ограничиваемые динамические маршруты используют
одну очередь на экземпляр. Исключения для точных публичных health/assets не
расширены; служебные сообщения MCP не обходят ограничитель или авторизацию.

Пределы включают запрос, проверяющий допуск в БД. FIFO гарантируется только в
одном экземпляре; несколько экземпляров делят SQL-лимит, но не очередь и не
порядок ожидания. После каждого отказа проверка повторяется не раньше секунды,
без удержания SQL-транзакции на время ожидания. Межэкземплярная справедливость
не обещается. Перезапуск не сохраняет ожидающие HTTP-запросы и не повторяет их.

Отмена соединения и остановка сервера прекращают ожидание. Таймаут возвращает
429 даже при незавершённой SQL-проверке; её слот остаётся занятым до завершения,
чтобы отменами нельзя было создать неограниченные фоновые запросы к БД. Поздний
ответ БД не запускает бизнес-операцию. Уже начатые бизнес-транзакции не отменяются.
Хеш допуска/сессия проверяются после ожидания: отзыв во время очереди действует.

Внутренние попытки допуска не считаются HTTP-отказами. Итоговый 429 регистрируется
один раз асинхронно: медленная, но работающая БД не даёт права терять счётчик.
Остановка сервера дожидается незавершённых записей. При ошибке БД используется
обезличенный, ограниченный по частоте fallback; полнота журнала при отказе
хранилища не гарантируется. Секреты и query в журнал не добавляются.

Граница защиты: ограничена очередь допуска, а не вся нагрузка приложения.
Отложенные записи аудита не имеют отдельного предела; при длительном замедлении
БД и потоке отказов они могут накапливаться в памяти/очереди пула. Это остаточный
эксплуатационный риск PoC, а не доказанная защита от произвольной нагрузки.
Аварийное завершение процесса также может потерять ещё не записанный аудит.

`test/outreach-http.test.ts` проверяет обычный SDK 1.30.0 без custom fetch:
connect, listTools, callTool и отсутствие transport errors. Остальной старый
регрессионный сценарий сохраняет свой pacing-адаптер и не заменяет эту проверку.
Локальный SDK не доказывает приёмку реальными ChatGPT/Codex через Timeweb:
AC-01/20 для этих сред остаются отдельными проверками. Зависимый почтовый этап
до их закрытия не начинать.

## Конфигурация после отдельного разрешения на размещение

Приложение работает в том же репозитории и нативном процессе Timeweb:

```sh
npm ci --include=dev --ignore-scripts
npm run build
npm run start:production
```

| Настройка | Значение |
|---|---|
| `OUTREACH_ENABLED` | `true` включает новый шлюз; отсутствие/false сохраняет прежний Telegram-only запуск |
| `DATABASE_URL` | Строка подключения к внешней PostgreSQL; TLS и сертификат по требованиям провайдера, проверку сертификата не отключать |
| `MCP_PUBLIC_ORIGIN` | HTTPS origin фактического домена без пути и query |
| `PORT` | Обычно 8080, либо предоставленный платформой порт |
| `MCP_TRUSTED_PROXY_CIDRS` | Только проверенные сети непосредственного прокси и доверенных промежуточных узлов |
| `MAIL_TRANSPORT_ENABLED` | `false` либо отсутствует |
| `TELEGRAM_ENABLED` | `false` либо отсутствует для первого рекламного среза |

Пустой список доверенных прокси безопасно игнорирует `X-Forwarded-For`, но за
Timeweb тогда ограничивается общий адрес прокси. Пока цепочка не подтверждена,
нельзя заявлять работающий лимит по реальному пользовательскому IP. При отказе
БД приложение не открывает реестр; `/healthz` сообщает только жизнь процесса.

Для одновременного подключения существующего Telegram-модуля нужно явно включить
`TELEGRAM_ENABLED=true` и предоставить прежние настройки `MCP_PROFILE`,
`PUBLISH_ENABLED`, реквизиты бота/канала. В новом шлюзе инструменты Telegram тоже
закрыты секретным MCP-логином. Такое включение и реальные отправки здесь не
выполнялись. Отключённый Telegram не инициализируется.

В показанном интерфейсе Timeweb отдельное поле переменных не подтверждено.
Ранее согласованный способ `env … npm run start:production` в поле запуска
технически остаётся возможным; его нельзя считать хранилищем секретов.
Готовую команду с рабочими секретами нельзя копировать в отчёт, Git или чат.

## Инициализация владельца и допуска

Операции выполняются владельцем в разрешённой среде с указанной конфигурацией:

```sh
npm run outreach:admin -- migrate
# Приватный JSON-файл содержит ровно поля login и password.
npm run outreach:admin -- init-owner < /secure/owner-input.json
# Новый адрес подключения сохраняется в НОВЫЙ файл с правами 0600, не в stdout.
npm run outreach:admin -- add-login /secure/mcp-connection.txt
# Отозвать допуск по несекретному ID, выданному предыдущей командой:
npm run outreach:admin -- revoke-login <credential-id>
```

Файлы с секретами находятся вне репозитория. Скрипт не перезаписывает существующий
файл адреса; повторная инициализация владельца не меняет его пароль. Полный URL
является секретом, кодирование `%HH` не шифрует его. Исходная длина — 16 символов,
длина кодированного значения может быть больше. Сервер декодирует один раз.

Перед рабочим допуском использовать синтетический маркер и проверить журналы
прокси/Timeweb, включая ошибочные запросы: полный query не должен сохраняться.
Приложение исключает query из собственного журнала, но настройка провайдера
здесь не проверена. HTTPS и `no-store` не удаляют query из access-логов.

## Проверка

```sh
npm run check
npm run build
npm test
# Дополнительный локальный WASM PostgreSQL, тесты без пропуска DB-сценариев:
npm run test:outreach
# Или настоящая тестовая PostgreSQL (только разрешённая тестовая БД):
OUTREACH_TEST_DATABASE_URL='<test-database-url>' npm run test:outreach
```

PGlite — только dev-зависимость для проверки SQL/HTTP. Рабочее приложение всегда
использует `pg` и внешнюю PostgreSQL. PGlite мультиплексирует соединения, а его
socket-адаптер игнорирует startup-настройку `search_path`; поэтому harness создаёт
новую временную БД для каждого тестового файла. Эти проверки не доказывают
сессионные свойства и конкурентность native PostgreSQL. Подготовлен workflow
`.github/workflows/outreach.yml` с PostgreSQL 16; он ещё не запускался в GitHub.

Тесты не отправляют почту и сообщения Telegram. `npm test` без адреса тестовой
БД явно пропускает интеграционные suite; их результат учитывается отдельно
по `npm run test:outreach`. Проверка восстановления внешней БД, реального
деплоя и интерфейса в браузере не считается выполненной по успеху unit/HTTP-тестов.

## Отключение

До любых изменений рабочей БД нужен резервный снимок. Миграция первого этапа
создаёт только таблицы с префиксом `outreach_`, выполняется под транзакционной
блокировкой и не изменяет данные Telegram. Для выключения модуля снять
`OUTREACH_ENABLED=true` и вернуть предыдущую команду запуска. Это не удаляет
БД и допуски; прежний Telegram-only режим имеет свою прежнюю политику доступа.
Схему не удалять автоматически при откате приложения.
