# Telegram Story Publisher — локальный код 0.2.0

Исходники и журнал разработки: [rtalyutin/Tg-mcp](https://github.com/rtalyutin/Tg-mcp),
ветка `main`. Публичное размещение пакета разрешено владельцем 16.09.2026.
Перед запуском владелец планирует сделать репозиторий приватным.
Актуальное состояние и следующий шаг — в `PROGRESS.md`.

Результаты шагов 1–2 ТЗ: локальный probe чтения состояния и независимое
ядро отправки, проверяемое на mock. На Timeweb ничего не развёрнуто,
постоянно работающего сервера и внешнего адреса нет. Это не готовый
коннектор для Timeweb/ChatGPT и не включённая автопубликация.

## Что реализовано

- TypeScript, Node.js 24, официальный `@modelcontextprotocol/sdk` 1.30.0.
- Настоящий Streamable HTTP `/mcp`, stateless transport, JSON-ответы.
- Единственный инструмент `get_publisher_status`, строгие входная и выходная
  схемы, `readOnlyHint: true`. Неизвестные поля запрещены.
- Состояние честно сообщает `publish_enabled: false`, `telegram_ready: false`,
  `reason_code: READ_ONLY_PROBE_TELEGRAM_NOT_CONFIGURED`.
- ID экземпляра неизменен в течение жизни сервера и меняется при новом старте.
- `/healthz` сообщает только работоспособность процесса, не готовность Telegram.
- Тестовая авторизация на всех MCP-запросах, запрет Origin и чужого Host,
  ограничение тела 16 KiB. Таймауты: заголовки 10 с, запрос/неактивность 15 с.
  Это защитные параметры локального прототипа, не обещание SLA.

Сервер слушает исключительно `127.0.0.1`. Bearer-токен — только локальная
тестовая фикстура. Не размещать этот вариант через proxy/tunnel, на Timeweb или
в интернете. Он не реализует OAuth и не подтверждает G2. Продакшен-режим,
другой HOST и включение публикации блокируются точкой запуска.

HTTP probe по-прежнему 0.1.0 и не регистрирует инструменты отправки.
В новой версии пакета добавлен отдельный модуль `src/publisher.ts`:
`Publisher.publish` и `Publisher.getAttemptStatus` с машинными схемами,
RAM-реестром, блокировкой канала, дедупликацией и классификацией результатов.
Вход разбирается строгой схемой; `chat_id`, `force` и другие лишние поля
не принимаются. Повторы возвращают сохранённое состояние без вызова sender.
При дедупликации по story_id возвращается исходный attempt_id.

Ядро НЕ соединено с HTTP probe. При будущем соединении необходимы один
общий Publisher на процесс, единый instance_id для status/publish/read,
проверка доступа до вызова ядра и реальная проверка типа/прав канала.
Нельзя создавать новый Publisher на каждый MCP-запрос.
Не объявлять G1–G3 или полную автопубликацию проверенными.

### Границы ядра

- Sender инъецируется внутренним кодом; реализованного сетевого Telegram
  adapter пока нет. В тестах это управляемый mock со счётчиком вызовов.
- Вызов sender совершается один раз для каждой части; неизвестность или
  отказ останавливают пакет. Ошибка/невалидный результат означают UNKNOWN,
  а не доказанное отсутствие поста. HTTP 429/5xx предстоит классифицировать
  реальному адаптеру; текущий gate проверяет только типизированные исходы.
- Pending sender остаётся IN_PROGRESS и удерживает блокировку; ядро не
  объявляет отмену по исчезновению клиента. Таймаут/AbortSignal и отсутствие
  скрытых сетевых повторов проверяются на этапе HTTP-адаптера.
- Реестр: по умолчанию 1000 попыток, без вытеснения. При заполнении новые
  попытки получают REGISTRY_FULL; старые остаются доступны. Полный текст
  не сохраняется в записях. Между процессами/перезапусками гарантии дублей нет.
  Замер `node --expose-gc scripts/measure-core.ts` от 16.09.2026: 1000
  попыток по 3 части, 3000 mock-вызовов; переполнение заблокировано, старый
  результат доступен без повтора. Прирост удержанной heap около 1,02 MB.
  Это один синтетический сценарий, не верхняя граница памяти или SLA.
- Ограничение текста: 256 KiB UTF-8, story_id: 256 UTF-16 единиц. Пустой
  текст, одиночные суррогаты и некорректные UUID отклоняются до отправки.
  Это технические границы локальной версии, не предел Telegram/SLA.
- Форматтер пока пропускает лишь цельный текст до 4096 UTF-16 единиц.
  Длинный текст отклоняется FORMATTER_NOT_IMPLEMENTED, не сокращается.
  Решение о последовательных постах сохранено; его Unicode/абзацная
  реализация — следующий шаг. Многочастная доставка тестируется на
  внутренней фикстуре форматтера с проверкой точного восстановления текста.
- Возвращаются копии результатов. message_url пока null: реальный канал
  и доступные ссылки не проверены. Нет команд очистки состояния/force/reset.
- JSON Schema в `schemas/` экспортируются командой `npm run schemas`.
  Дополнительные runtime-проверки UTF-8 размера, непустоты и Unicode
  выполняет Zod-модуль; JSON Schema сам по себе их полностью не выражает.

Разбиение сказки, реальный Telegram-адаптер, OAuth, Dockerfile и подключение
существующей задачи ещё не реализованы. Ключей Telegram в пакете нет.

## Воспроизведение

Требуется Node.js 24 и npm. Зависимости закреплены в package-lock.json.

```sh
npm ci --ignore-scripts
npm run check
npm test
```

Тесты самостоятельно запускают сервер на свободном локальном порту и создают
временный случайный токен в памяти. Токен Telegram и интернет для самих тестов
не нужны. Загрузка зависимостей при `npm ci` требует доступа к npm.

Для ручного локального запуска скопировать `.env.example` в `.env`, заполнить
`LOCAL_PROBE_TOKEN` новым случайным секретом: 32–256 символов base64url.
Не использовать токен Telegram. Затем:

```sh
node --env-file=.env src/main.ts
```

Официальный MCP-клиент подключается к `http://127.0.0.1:3000/mcp` с заголовком
`Authorization: Bearer <LOCAL_PROBE_TOKEN>`. Готовые примеры работы клиента
есть в `test/server.test.ts`. Токен не передавать в URL и не сохранять в архиве.
В этом локальном профиле браузерные Origin не разрешены, в том числе у Inspector.

Сгенерированные проверки — `verification/test.tap`; независимые сценарии и
ограничения — `QA-INDEPENDENT.md` (probe) и `QA-CORE-2026-09-16.md` (ядро).
Состояние продолжения — `PROGRESS.md`.
В архив не включаются node_modules, `.env` и секреты. Исходники, lockfile и
результаты проверки — артефакты разработки, не хранилище публикаций приложения.
