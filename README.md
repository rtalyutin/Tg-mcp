## Timeweb: один шаг после обновления main

Пересобрать новую версию. Команды на скриншоте владельца уже подходят:

- Сборка: `npm ci --include=dev --ignore-scripts && npm run build`.
- Запуск: `npm run start:production`.
- Проверка состояния: `/healthz`.
- Node.js 24; один процесс/реплика; без своего Dockerfile и БД.
- Переменные для первого read-only запуска не требуются.

Подключение ChatGPT без OAuth: `https://rtalyutin-tg-mcp-fb9b.twc1.net/mcp`.
Подробности: [TIMEWEB-NATIVE.md](TIMEWEB-NATIVE.md).
Успешное подключение и фоновый вызов требуют реальной проверки; локальные
тесты их не доказывают. Публикация выключена, генератор и расписание не изменены.

**Приватность GitHub не защищает работающий HTTP endpoint.** В публичном режиме
у сервера нет проверки личности вызывающего. Сейчас открыт только статус без
Telegram-конфигурации; если позже включить публичную публикацию, любой клиент,
знающий домен, сможет публиковать произвольный текст в заданный канал.
Ограничение одной новой сказки в минуту лишь снижает частоту, а не закрывает доступ.

Для первого запуска не используйте прежний файл с MCP_PATH_SECRET: старые
настройки авторизации сохраняют fail-closed поведение. Без режима, но с любым
старым auth-полем, приложение не переключится молча в public.
Явные `oauth` и `secret_path` доступны как альтернативы; выбранный вариант — public.

## Позднейшее включение публикации

Токен Telegram-бота остаётся обязательным для отправки: приватная репа его
не заменяет, в исходники его не добавлять. Нужны явные `MCP_AUTH_MODE=public`,
`MCP_PROFILE=publisher`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHANNEL_ID` и разрешённое
`PUBLISH_ENABLED=true`. Профиль publisher без явного выбора public отклоняется.
Эти настройки сейчас не применены; реальные Telegram-публикации не выполнялись.

### Несколько заданий и каналов

Один экземпляр приложения и один Telegram-бот могут обслуживать несколько
каналов. Вместо `TELEGRAM_CHANNEL_ID` задайте
`TELEGRAM_TASK_CHANNELS=bear=-100111,fox=@examplechannel` (примерные значения).
Ключ слева — постоянный `task_id` задания; справа — числовой ID или
публичное имя канала `@username`.
При вызове `publish_story` задание передаёт свой `task_id` вместе с прежними
`story_id`, `attempt_id`, `expected_instance_id` и полным `text`. Сервер
выбирает канал только по своей таблице: произвольный `chat_id` запрещён.
Отсутствующий или незарегистрированный `task_id` в этом режиме отклоняется
без отправки. Для прежнего варианта с одним `TELEGRAM_CHANNEL_ID` поле
`task_id` остаётся необязательным.

Пример для поля команды запуска Timeweb (подставить свои ID и токен в панели):

```sh
env MCP_AUTH_MODE=public MCP_PROFILE=publisher PUBLISH_ENABLED=false TELEGRAM_BOT_TOKEN='ТОКЕН' TELEGRAM_TASK_CHANNELS='bear=-100111,fox=-100222' npm run start:production
```

Сначала оставьте `PUBLISH_ENABLED=false`. `get_publisher_status` показывает
готовность по каждому `task_id`; бот должен быть администратором каждого
целевого канала с правом публикации. Для `@username` ответ также показывает
`resolved_channel_id`: сервер сверяет имя канала, проверяет права и отправляет
по полученному числовому ID. Внутри процесса смена ID под тем же именем
блокирует дальнейшую отправку; после перезапуска эта память теряется.
Для постоянной привязки канала перенесите найденный числовой ID в настройку.
При `telegram_ready=false` поле `task_status[].check_code` уточняет этап:
`BOT_CHECK_FAILED` — не удалось проверить токен и бота;
`CHANNEL_CHECK_FAILED` — не удалось прочитать канал;
`BOT_MEMBERSHIP_CHECK_FAILED` — не удалось проверить участие бота;
`BOT_NOT_ADMIN` или `POST_PERMISSION_MISSING` — нужно изменить права бота.
`CHANNEL_MISMATCH` и `CHANNEL_ID_CHANGED` требуют сверить привязку канала.
Ответы Telegram и токен в статус не включаются. Эта проверка доступна и при
`PUBLISH_ENABLED=false`; верхнее `reason_code=PUBLISH_DISABLED` не отменяет
отдельный результат проверки канала.
При включении отправки сохраняются
общая блокировка и лимит одной новой публикации в минуту на весь процесс;
для совпадающих по времени заданий нет очереди. Неизвестный исход отправки
в одном канале не запускает автоматический повтор и не меняет другой канал.

В публичном MCP `task_id` указан самим вызывающим, поэтому сервер не может
доказать, что вызов пришёл из соответствующей фоновой задачи. Любой, кто
знает публичный адрес, сможет выбрать любой настроенный `task_id`, когда
публикация включена. Приватный репозиторий этого не предотвращает.

Полный текст идёт последовательными постами. UNKNOWN/частичная отправка —
остановка, ручная проверка канала и никакого автоматического повтора.
Реестр, лимит 60 секунд и состояние только в RAM, теряются после рестарта.

Ниже описаны сохранённые локальные профили. `npm start` и `start:built`
остаются безопасным loopback probe: их не выставлять в интернет.

## Что реализовано

- TypeScript, Node.js 24, официальный `@modelcontextprotocol/sdk` 1.30.0.
- Настоящий Streamable HTTP `/mcp`, stateless transport, JSON-ответы.
- Безопасный read-only профиль по-прежнему содержит единственный инструмент
  `get_publisher_status`, строгие схемы и `readOnlyHint: true`. Неизвестные
  поля запрещены.
- Состояние честно сообщает `publish_enabled: false`, `telegram_ready: false`,
  `reason_code: READ_ONLY_PROBE_TELEGRAM_NOT_CONFIGURED`.
- ID экземпляра неизменен в течение жизни сервера и меняется при новом старте.
- `/healthz` сообщает только работоспособность процесса, не готовность Telegram.
- Тестовая авторизация на всех MCP-запросах, запрет Origin и чужого Host,
  ограничение тела 16 KiB. Таймауты: заголовки 10 с, запрос/неактивность 15 с.
  Это защитные параметры локального прототипа, не обещание SLA.

Сервер слушает исключительно `127.0.0.1`. Bearer-токен — только локальная
тестовая фикстура. Не размещать этот вариант через proxy/tunnel, на Timeweb или
в интернете. Он не реализует OAuth и не подтверждает G2. Продакшен-режим,
другой HOST и включение публикации блокируются точкой запуска.

HTTP probe по-прежнему 0.1.0 и не регистрирует инструменты отправки. Точка
запуска `src/main.ts` использует только этот профиль и отвергает production,
внешний HOST и включение публикации.

Пакет 0.7.0 содержит отдельный `startLocalIntegratedPublisher` только для
локальной сквозной проверки. Он создаёт ровно один `Publisher` и один
`TelegramSender` на жизнь процесса и регистрирует три MCP-инструмента:
`get_publisher_status`, `publish_story`, `get_publish_attempt`. Состояние RAM
сохраняется между MCP-запросами и разными клиентскими соединениями. Этот
harness требует `http://127.0.0.1:<port>` как Telegram API root; официальный
или любой внешний адрес отклоняется до запуска сервера. Он не экспортирован
как production entrypoint и не является способом подключения ChatGPT.

Модуль `src/publisher.ts` реализует:
`Publisher.publish` и `Publisher.getAttemptStatus` с машинными схемами,
RAM-реестром, блокировкой канала, дедупликацией и классификацией результатов.
Вход разбирается строгой схемой; `chat_id`, `force` и другие лишние поля
не принимаются. Повторы возвращают сохранённое состояние без вызова sender.
При дедупликации по story_id возвращается исходный attempt_id.

Ядро не соединено с безопасным read-only probe, но соединено с отдельным
локальным integration harness. В нём едины Publisher и `instance_id` для
status/publish/read. Реальная проверка типа канала и прав бота ещё не
реализована: `telegram_ready` задаётся тестовой конфигурацией. Не объявлять
G1–G3 или полную автопубликацию проверенными.

### Границы ядра

- `src/telegram.ts` реализует `sendMessage`: один POST с JSON `chat_id` и
  исходным `text`, без `parse_mode`, прикладных повторов и перехода по
  редиректам. Production endpoint закреплён за `https://api.telegram.org`;
  HTTP разрешён только для loopback mock-тестов. Токен находится в пути по
  формату Bot API, но не включается в тело, результат или журналы приложения.
- Вызов sender совершается один раз для каждой части; неизвестность или
  отказ останавливают пакет. Ошибка/невалидный результат означают UNKNOWN,
  а не доказанное отсутствие поста. Подтверждением считается только HTTP 200,
  JSON `ok: true` и положительный безопасный `message_id`. 429 означает
  `RATE_LIMITED`, 401/403 — `BOT_FORBIDDEN`, прочие явные 4xx —
  `SEND_REJECTED`. Таймаут, обрыв, 408, 5xx, редирект, невалидный или слишком
  большой ответ дают UNKNOWN и требуют ручной проверки канала.
- Pending sender остаётся IN_PROGRESS и удерживает блокировку; ядро не
  объявляет отмену по исчезновению клиента. Таймаут ограничен 1–60000 мс
  (по умолчанию 15 с). Mock HTTP проверяет отсутствие последующих частей и
  новых запросов после UNKNOWN, включая повтор попытки и новый attempt_id.
- Реестр: по умолчанию 1000 попыток, без вытеснения. При заполнении новые
  попытки получают REGISTRY_FULL; старые остаются доступны. Полный текст
  не сохраняется в записях. Между процессами/перезапусками гарантии дублей нет.
  Замер `node --expose-gc scripts/measure-core.ts` от 16.09.2026: 1000
  попыток по 3 части, 3000 mock-вызовов; переполнение заблокировано, старый
  результат доступен без повтора. Прирост удержанной heap около 1,02 MB.
  Это один синтетический сценарий, не верхняя граница памяти или SLA.
- Ограничение текста: 256 KiB UTF-8, story_id: 256 UTF-16 единиц. Пустой
  текст, одиночные суррогаты и некорректные UUID отклоняются до отправки.
  Это технические границы локальной версии, не предел Telegram/SLA.
- Форматтер `src/formatter.ts` подключён к ядру по умолчанию. Он сохраняет
  полный текст и разделители: `parts.join('') === text`. Нет нормализации,
  обрезки, нумерации или служебных подписей. Приоритет разрезов: последний
  допустимый конец абзаца → предложения → слова → расширенной графемы.
  Перенос строки (LF/CRLF/CR/Unicode line/paragraph separator) считается
  границей абзаца. Границы предложений, слов и графем задаёт ICU Node.js
  через `Intl.Segmenter('ru', ...)`; версия ICU может влиять на места разреза.
- Бюджет каждой части — не более 4096 UTF-16 единиц. Это консервативное
  инженерное ограничение, а не доказательство конкретного подсчёта Telegram:
  [Bot API, проверено 17.09.2026](https://core.telegram.org/bots/api#sendmessage)
  указывает 1–4096 символов после разбора entities. Astral-символы занимают
  две UTF-16 единицы, поэтому некоторые emoji-тексты разбиваются раньше.
  Реальную приёмку и отображение Unicode в канале ещё предстоит проверить.
- Каждый разрез проверяется по графемам всего исходного текста. ZWJ-эмодзи,
  флаги, модификаторы, CRLF и комбинируемые знаки не разрываются. Неделимая
  графема сверх бюджета даёт `TEXT_GRAPHEME_TOO_LONG` до первого send.
  Если невозможно разбить текст без пустых/пробельных постов, возвращается
  `TEXT_CANNOT_SPLIT`; пробелы при этом не удаляются. Алгоритм заранее
  проверяет выполнимость остатка, чтобы предпочтительный разрез не создавал
  искусственный отказ на длинных пробельных последовательностях.
- Все части проверяются до отправки, включая результат внутренней подмены
  форматтера. Последовательная доставка и остановка после неподтверждённой
  части проверяются с настоящим форматтером и mock sender, не Telegram.
- Возвращаются копии результатов. message_url пока null: реальный канал
  и доступные ссылки не проверены. Нет команд очистки состояния/force/reset.
- JSON Schema в `schemas/` экспортируются командой `npm run schemas`.
  Дополнительные runtime-проверки UTF-8 размера, непустоты и Unicode
  выполняет Zod-модуль; JSON Schema сам по себе их полностью не выражает.

Адаптер подключён к MCP только в loopback integration harness и проверен с
локальным mock HTTP, не с Telegram. TelegramReadinessChecker подключён к новому `startLocalCheckedPublisher`,
который принимает только loopback mock Telegram. Публичный production entrypoint
и OAuth ещё не реализованы.
Подготовлены сборка JavaScript без собственного Dockerfile и блок передачи
публикации существующей задаче; подключение задачи ещё не выполнено. Реальных ключей Telegram
в репозитории нет.

## Воспроизведение

Требуется Node.js 24 и npm. Зависимости закреплены в package-lock.json.

```sh
npm ci --ignore-scripts
npm run check
npm test
```

Тесты самостоятельно запускают сервер на свободном локальном порту и создают
временный случайный токен в памяти. Токен Telegram и интернет для самих тестов
не нужны. Загрузка зависимостей при `npm ci` требует доступа к npm.

Для ручного локального запуска скопировать `.env.example` в `.env`, заполнить
`LOCAL_PROBE_TOKEN` новым случайным секретом: 32–256 символов base64url.
Не использовать токен Telegram. Затем:

```sh
node --env-file=.env src/main.ts
```

Официальный MCP-клиент подключается к `http://127.0.0.1:3000/mcp` с заголовком
`Authorization: Bearer <LOCAL_PROBE_TOKEN>`. Готовые примеры работы клиента
есть в `test/server.test.ts`. Токен не передавать в URL и не сохранять в архиве.
В этом локальном профиле браузерные Origin не разрешены, в том числе у Inspector.

Сгенерированные проверки — `verification/test.tap`; независимые сценарии и
ограничения — `QA-INDEPENDENT.md` (probe), `QA-CORE-2026-09-16.md` (ядро),
`QA-FORMATTER-2026-09-17.md`, `QA-TELEGRAM-2026-09-18.md` и
`QA-MCP-2026-09-19.md` и `QA-NATIVE-2026-09-19.md`.
Состояние продолжения — `PROGRESS.md`.
В архив не включаются node_modules, `.env` и секреты. Исходники, lockfile и
результаты проверки — артефакты разработки, не хранилище публикаций приложения.

## Проверка готовности и остановка (0.7.0)

`startLocalCheckedPublisher` использует те же три MCP-инструмента, но не принимает
`telegramReady` как ручной флаг. Он запускает настоящую последовательность
getMe → getChat → getChatMember на обязательном локальном mock endpoint.
Старый `startLocalIntegratedPublisher` сохранён как отдельная тестовая фикстура
с заданной готовностью. `src/main.ts` по-прежнему запускает только read-only probe.

Каждое чтение статуса обновляет проверку; completed-result cache/таймера нет.
Одновременные чтения объединяются в одну выполняющуюся проверку. Новая попытка
проверяет права перед первым send, при необходимости присоединяясь к текущей
проверке. При регистрации она получает блокировку канала ДО ожидания проверки:
повтор той же попытки/сказки читает IN_PROGRESS, другая получает BUSY. Непригодный
формат, stale instance, отключение и дубликаты не запускают preflight. Отказ
preflight сохраняется в реестре; восстановление прав не переотправляет ту же сказку.

Неудачная отправка сбрасывает снимок готовности. Старый read-ответ, пришедший
после сброса/остановки, не восстанавливает его. Новая проверка может снова
подтвердить права: это не доказательство успешной доставки прежней попытки.
`get_publish_attempt` и `/healthz` не обращаются к Telegram. Статус использует
честный `openWorldHint=true`, поскольку checked-профиль выполняет сетевое чтение.

`stop()` необратим для данного экземпляра: запрещает новые попытки/части и
дожидается текущего сетевого запроса. При подтверждении промежуточной части —
PARTIAL/SHUTTING_DOWN и сохранённые ID; при неизвестном исходе — UNKNOWN,
а не «ничего не отправлено». Если последняя часть подтверждена, итог PUBLISHED.
Во время остановки чтение/дедупликация сохраняются, статус SHUTTING_DOWN.
`close()` вызывает stop, затем закрывает HTTP без принудительного обрыва ответа
текущей публикации. Повторный close возвращает тот же Promise.

`installShutdownHandlers(app.close)` подключает SIGTERM/SIGINT в точке запуска.
Прерывать уже начатый запрос и отзывать Telegram-публикацию он не пытается.
Исходящий timeout остаётся 15 с (1–60000 мс) на одну readiness-последовательность
или send; HTTP timeout прежний. Это не SLA: при раннем SIGKILL платформы исход
считается неизвестным, а RAM теряется. Production-интеграцию сигналов и период
остановки Timeweb нужно проверить при разрешённом внешнем выпуске.
