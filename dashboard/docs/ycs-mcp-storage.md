# Данные Dashboard через YCS-mcp

Цель: сначала установить проверенный частичный снимок, затем обновлять его
регулярно из доступных проверяемых источников. Неподтверждённые данные не
заполнять догадками. Частный список исключений применять **до чтения**
источников, при следующих обновлениях сохранять в JSON. Команды не возвращают
содержимое частного снимка; они возвращают контрольную сумму, дату и количество записей.

## Доступ в Timeweb Cloud

1. Использовать существующую PostgreSQL-базу и уже настроенного пользователя
   YCS из `DATABASE_URL`. Новую базу и новых пользователей не создавать.
   Миграция добавляет схему `dashboard` и хранит в ней все свои таблицы,
   включая журнал миграций. Существующие таблицы YCS не мигрируются.
2. Убедиться, что этот пользователь может создать схему и таблицы в текущей
   базе. Если прав не хватает, миграция завершится ошибкой без импорта. URI и
   пароль остаются только в действующей переменной `DATABASE_URL`; их не
   переносить в GitHub, issue и открытый чат.
3. После выпуска backend вызвать в YCS-mcp `get_dashboard_storage_access {}`
   со своим рабочим логином.
   Поле `credential_id` нужно для переменной ниже. `permitted_for_migration` и
   `permitted_for_updates` станут `true` после настройки приложения.

Переменная окружения приложения для установки и регулярных обновлений:

| Переменная | Значение |
| --- | --- |
| `DASHBOARD_SNAPSHOT_MCP_CREDENTIAL_ID` | `credential_id` владельца из команды выше |

Значение `DASHBOARD_MIGRATION_ENABLED` не учитывается. Доступ к команде
установки определяется существующим подключением `DATABASE_URL` и совпадением
MCP-логина с `DASHBOARD_SNAPSHOT_MCP_CREDENTIAL_ID`.

`DATABASE_URL` YCS Outreach не менять. Личный `/dashboard/api/snapshot`
использует существующий вход владельца через `/login`; включать
`DASHBOARD_ENABLED` ради него не нужно. Если позже включается канонический
`/dashboard/mcp`, он использует ту же БД и роль из `DATABASE_URL`, но требует
отдельного bearer-токена.

## Накатить миграции на уже установленный Dashboard

Production-миграцию запускает backend при первом вызове `update_dashboard_snapshot`.
`write_database` не меняет схему и для миграции не подходит. Для уже заполненной
базы:

1. Выпустить backend с миграциями 005–007. Существующие переменные приложения
   и `DATABASE_URL` оставить в Timeweb; не переносить их в репозиторий.
2. Вызвать `get_dashboard_storage_access {}` и проверить
   `permitted_for_updates: true`.
3. Вызвать `update_dashboard_snapshot` с полным актуальным `snapshot`, сохранив
   существующие ID, исключения и источники. `project_groups` передавать отдельным
   аргументом рядом со `snapshot`, если нужно явно заменить членство проектов;
   для уже сохранённых назначений его можно опустить.
4. Backend применит отсутствующие миграции по порядку, сохранит обновление и
   выполнит независимое чтение. Проверить `readback_verified: true`,
   `project_groups_digest` и ожидаемые числа. Затем через `read_database`
   убедиться, что в `dashboard.dashboard_schema_migration` есть версии 005–007,
   а `dashboard.projects_groups` и `dashboard.daily_result` доступны.

Миграция 005 переносит связи из текущего snapshot: `display_group_ids`
(или `display_group_id`) сопоставляются с заголовками из `project_groups`.
Если хотя бы у одного проекта нет связи, миграция целиком откатится с
`DASHBOARD_PROJECT_GROUPS_REQUIRED`; сначала нужно указать его реальный
`group_code`, не выводить группу из названия проекта. Миграция 006 создаёт
закрытый дневной журнал. Повтор вызова безопасен: применённые версии
пропускаются, а контрольные суммы миграций сверяются.

Не вызывай `install_dashboard_snapshot` для уже заполненной базы: это путь
первичной установки, который отклоняет снимок, отличающийся от сохранённого.

## Однократная установка

После выпуска кода и настройки переменной вызвать через YCS-mcp:

```json
{"name":"install_dashboard_snapshot","arguments":{"snapshot":{"schema":"dashboard-curated-snapshot/1","coverage":"partial","...":"остальные поля из частного JSON"},"project_groups":[{"project_id":"project-id","group_code":"Название группы"}]}}
```

Аргумент `snapshot` — частный JSON, проверенный вместе с источниками
и исключениями; пример выше схематичный и не проходит проверку. Команда
проверяет структуру, ссылки на источники и назначение группы каждому проекту,
применяет миграции до текущей версии в схеме `dashboard`, атомарно сохраняет
снимок и строки `dashboard.projects_groups`, затем перечитывает обе части
через новое соединение с тем же логином. Успех: актуальный `schema_version`, ожидаемые числа,
контрольную сумму записанного снимка и `verified: true`.
Повтор той же установки идемпотентен; после обновления снимка повторная
установка старого файла отклоняется, чтобы не затереть новые данные.

`project_groups` обязателен при первой установке и содержит одну или несколько
связей для каждого проекта. Один проект может входить в несколько групп.
Список групп не зашит в код; новые `group_code` появятся из сохранённых строк.

Полный `snapshot` при установке и обновлении ограничен **512 000 байтами UTF-8**
после `JSON.stringify(snapshot)`. При превышении обе команды возвращают
`DASHBOARD_SNAPSHOT_TOO_LARGE` с `actual_bytes` и `max_bytes` без записи.
В профиле без Telegram worker MCP HTTP допускает сверх обычных 65 536 байт тела
только для двух команд снимка у настроенного логина; конверт JSON-RPC ограничен
4 194 304 байтами, чтобы принять экранированный Unicode и связи с группами.
Это отдельный предел всего запроса. При включённом worker
действует его существующий транспортный лимит 10 МБ. Смысловой предел снимка
остаётся 512 000 байт в обоих профилях.

`DASHBOARD_SNAPSHOT_MCP_CREDENTIAL_ID` оставить для регулярной синхронизации.
Отдельные URL чтения и записи не нужны.

## Суточная история изменений

Миграция 006 создаёт закрытую `dashboard.daily_result`. Миграция 007 разрешает
`dialog_cutoff_at=NULL` для частичного результата, когда полного перечисления
диалогов не было. Заполнять это поле текущим временем для видимости успешного
обхода запрещено. Ежедневное задание читает предыдущий результат и группы
через `@FullaccessbdYCS`, собирает доступные подтверждённые события и добавляет
ровно одну строку на отчётную дату (`report_date`). В строке лежат полный
результат дня, связи проектов с группами, изменения, digest снимка и фактическое
покрытие. Тексты диалогов целиком в журнал не копируются.

`dashboard.source_event` — входной журнал, а не доказательство полного охвата
ChatGPT. Для каждого подтверждённого факта нужен стабильный идентификатор
сообщения/события, ревизия, ID диалога, время факта, ссылка и короткая
структурированная дельта в `payload`; неизвестные поля остаются неизвестными.
Событие добавляют после проверки источника, повтор сверяют по
`(source_id,native_id,revision)` и digest. Исключённые владельцем проекты
фильтруют до чтения содержимого. Если источник даёт лишь часть бесед,
`dialog_scan` указывает перечисленные области и пробелы, `coverage='partial'`,
`dialog_cutoff_at=NULL`. Пустой журнал означает отсутствие поступивших
событий, а не отсутствие изменений во всех беседах.

`prepared` допускает только повтор той же попытки и перевод в `applied` после
readback снимка и журнала. `applied` и `baseline_only` неизменяемы. Повтор за
уже закрытую дату сначала читает существующую строку; совпадающий результат
считается повтором, отличающийся требует отдельной коррекции истории и не
перезаписывает её. Роль HTTP runtime не имеет доступа к дневному журналу.
Первую строку можно создать только из реально прочитанного текущего снимка и
всех его связей; она создаёт `baseline_only` с `changes=[]`, `coverage='partial'`
и `dialog_cutoff_at=NULL` без выдуманной суточной дельты. Даты после baseline
обрабатываются по порядку. Известные факты с датами относятся к своим дням,
неизвестные пропуски остаются в `dialog_scan`; глобальная полнота не заявляется.
Перед записью `prepared` ежедневная задача проверяет полный снимок и размер
его сериализации, неизменность ID/источников/исключений, все связи с группами,
а также digest именно той сериализации, которую отправит backend. Если ранее
сохранён `prepared`, сначала восстановить его точный payload и сверить digest;
следующую дату не начинать до `applied`.

Перед первым ежедневным запуском проверить, что миграции 006–007 применены, а
`@FullaccessbdYCS` видит `dashboard.daily_result` и `dashboard.projects_groups`.
До этого задание должно сообщать о блокировке схемы и не писать результат.

## Каждое обновление

1. Исключить частный проект **до сбора**. Из доступных источников сформировать
   новую проверяемую выборку, сохранить `coverage: "partial"`, ссылки на
   источники, прежние ID, записи источников и список исключений. Не удалять
   ранее подтверждённые строки просто потому, что источник временно недоступен.
2. Вызвать `get_dashboard_snapshot_state {}` и проверить текущий охват и дату.
3. Вызвать `update_dashboard_snapshot` с полным новым `snapshot`. При первом
   обновлении после добавления групп приложить `project_groups` для всех текущих
   проектов. В дальнейшем передавать назначения для новых проектов и явных
   переносов между группами; сохранённые связи остаются в таблице.
   Новый проект без назначения блокирует всё обновление и возвращает его ID.
   Назначение не выводить из названия автоматически.
   Команда не
   требует предыдущую контрольную сумму, но отклоняет потерю ID, исключения
   и старых источников, атомарно обновляет снимок и назначения, применяет
   недостающие миграции и перечитывает обе части через новое соединение.
   Проверить `readback_verified: true`, итоговую контрольную сумму,
   `project_groups_digest`
   и числа. При ошибке перечитать состояние и сверить источники перед повтором.
4. Проверить личный `/dashboard/api/snapshot` после входа через `/login`;
   без сессии приватный ответ должен оставаться закрытым. Если источник
   недоступен, фиксировать пробел охвата, а не выдумывать прогресс.

Ежедневное задание синхронизации должно выполнять эти шаги после активации
сервиса и сообщать о блокировке, если YCS-mcp ещё не показывает новые команды,
роли или исходные данные недоступны. Установка инструмента сама по себе не
делает данные автоматически полными и не запускает запись по расписанию.
