# Данные Dashboard через YCS-mcp

Цель: сначала установить проверенный частичный снимок, затем обновлять его
регулярно из доступных проверяемых источников. Неподтверждённые данные не
заполнять догадками. Частный список исключений применять **до чтения**
источников, при следующих обновлениях сохранять в JSON. Команды не возвращают
содержимое частного снимка; они возвращают digest, дату и количество записей.

## Доступ в Timeweb Cloud

1. Создать отдельную PostgreSQL-базу Dashboard (можно в существующем кластере).
   Это **другая база**, чем рабочая база YCS Outreach из `DATABASE_URL`.
2. Подготовить три логина к этой базе: миграционный владелец с правом создавать
   схему и таблицы, `dashboard_snapshot_reader` и `dashboard_snapshot_writer`.
   У двух последних изначально не должно быть широких прав на таблицы. В панели
   Timeweb новый пользователь по умолчанию получает полные права ко всем базам:
   развернуть «Показать привилегии» и ограничить их перед сохранением. На
   минимальном тарифе создание пользователей недоступно. Если нельзя сделать
   две узкие роли, настройку остановить: проверка привилегий команду отклонит.
3. Получить три URI подключения из панели базы, с разными именами пользователей
   и паролями. Использовать TLS согласно настройкам кластера. Пароли и частный
   JSON не хранить в GitHub, issue, журнале команд и открытом чате.
4. В YCS-mcp вызвать `get_dashboard_storage_access {}` со своим рабочим логином.
   Поле `credential_id` нужно для переменных ниже. `permitted_for_migration` и
   `permitted_for_updates` станут `true` после настройки приложения.

Переменные окружения приложения на этапе первой установки:

| Переменная | Значение |
| --- | --- |
| `DASHBOARD_SNAPSHOT_MCP_CREDENTIAL_ID` | `credential_id` владельца из команды выше |
| `DASHBOARD_MIGRATION_ENABLED` | `true` |
| `DASHBOARD_MIGRATION_DATABASE_URL` | PostgreSQL URI миграционного владельца отдельной базы |
| `DASHBOARD_SNAPSHOT_READ_DATABASE_URL` | URI роли `dashboard_snapshot_reader` той же базы |
| `DASHBOARD_SNAPSHOT_WRITE_DATABASE_URL` | URI роли `dashboard_snapshot_writer` той же базы |
| `DASHBOARD_APPROVED_SNAPSHOT_DIGEST` | SHA-256 от точного `JSON.stringify(snapshot)` утверждённого частного JSON |

`DATABASE_URL` YCS Outreach не менять. Для личного экрана также нужны уже
предусмотренные `DASHBOARD_DATABASE_URL` (отдельная рабочая роль Dashboard),
`DASHBOARD_ENABLED=true` и настройки входа владельца из
[postgres-runtime-role.md](./postgres-runtime-role.md). Если рабочая роль
Dashboard ещё не создана, сначала можно установить снимок через MCP, а экран
включить позже.

## Однократная установка

После выпуска кода и настройки переменных вызвать через YCS-mcp:

```json
{"name":"install_dashboard_snapshot","arguments":{"expected_digest":"<утверждённый SHA-256>","snapshot":{"schema":"dashboard-curated-snapshot/1","coverage":"partial","...":"остальные поля из частного JSON"}}}
```

Аргумент `snapshot` — точный частный JSON, уже проверенный вместе с источниками
и исключениями; пример выше схематичный и не проходит проверку. Команда
сверяет digest с аргументом и настройкой приложения, применяет миграции до
версии 004, выдаёт узкие права ролям, записывает одну строку и перечитывает её
через `dashboard_snapshot_reader`. Успех: `schema_version: 4`, ожидаемые числа,
тот же digest и `verified: true`. До вызова нужно создать обе узкие роли.
Повтор той же установки идемпотентен; после обновления снимка повторная
установка старого файла отклоняется, чтобы не затереть новые данные.

После успеха удалить из окружения `DASHBOARD_MIGRATION_ENABLED`,
`DASHBOARD_MIGRATION_DATABASE_URL` и `DASHBOARD_APPROVED_SNAPSHOT_DIGEST`,
перезапустить приложение. Миграции следующих версий запускать как отдельную
операцию выпуска. `DASHBOARD_SNAPSHOT_MCP_CREDENTIAL_ID`, URL чтения и URL
записи оставить для регулярной синхронизации.

## Каждое обновление

1. Исключить частный проект **до сбора**. Из доступных источников сформировать
   новую проверяемую выборку, сохранить `coverage: "partial"`, ссылки на
   источники, прежние ID, записи источников и список исключений. Не удалять
   ранее подтверждённые строки просто потому, что источник временно недоступен.
2. Вызвать `get_dashboard_snapshot_state {}` и запомнить текущий `digest`.
3. Вызвать `update_dashboard_snapshot` с полным новым `snapshot` и
   `expected_current_digest`, равным считанному digest. Команда отклоняет
   устаревшую версию, потерю ID/исключения/старых источников, обновляет одну
   строку и перечитывает через роль чтения. Проверить `readback_verified: true`,
   новый digest и числа. При конфликте заново считать состояние и сверить
   источники перед повтором.
4. Проверить личный `/dashboard/api/snapshot` после входа через `/login`;
   без сессии приватный ответ должен оставаться закрытым. Если источник
   недоступен, фиксировать пробел охвата, а не выдумывать прогресс.

Ежедневное задание синхронизации должно выполнять эти шаги после активации
сервиса и сообщать о блокировке, если YCS-mcp ещё не показывает новые команды,
роли или исходные данные недоступны. Установка инструмента сама по себе не
делает данные автоматически полными и не запускает запись по расписанию.
